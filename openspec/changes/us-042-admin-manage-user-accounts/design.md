## Context

本 US 实现管理后台的用户账号管理功能，包括用户列表查询、重置密码、修改手机号/邮箱、配置角色权限。所有敏感操作需记录审计日志。

## Goals / Non-Goals

**Goals:**

- 管理员可按身份、注册时间筛选用户
- 管理员可查看用户详情
- 管理员可重置密码、修改手机号、修改邮箱
- 管理员可配置用户角色权限

**Non-Goals:**

- 不实现用户自助修改资料（由 US-005/US-008 实现）
- 不实现账号注销（由 US-007 实现）
- 不实现复杂的组织架构权限

## Decisions

1. **用户表增加 `version` 乐观锁字段**
   - 理由：防止并发修改同一用户资料导致数据覆盖
   - 替代方案：数据库行锁 —— rejected，乐观锁对读多写少场景更友好

2. **`force_change_password` 字段控制首次登录改密**
   - 理由：统一登录入口即可感知是否需要强制改密，无需额外状态表
   - 替代方案：单独维护 token 表 —— rejected，增加复杂度

3. **角色通过 `user_role` 关联表配置**
   - 理由：支持多对多关系，一个用户可拥有多个角色
   - 替代方案：user 表增加 `role` 字段 —— rejected，无法支持多角色

4. **手机号/邮箱唯一性校验后置写入前加唯一索引兜底**
   - 理由：先查询再写入可能存在并发竞态，唯一索引保证最终一致性

## Risks / Trade-offs

- **[Risk]** 管理员误重置用户密码导致用户无法登录 → **Mitigation**: 二次确认弹窗 + 审计日志
- **[Risk]** 批量导出大量用户数据造成性能压力 → **Mitigation**: 导出异步化，限制单次 10000 条
- **[Risk]** 修改手机号后原手机号仍被缓存 → **Mitigation**: 更新成功后失效用户详情与登录缓存

## Migration Plan

1. 执行 Knex migration 确保 `user` 表存在 `version`、`force_change_password` 字段
2. 确认 `user.phone` 与 `user.email` 已设置唯一索引
3. 部署后端接口与管理端页面
4. 回滚：删除新增字段并回退代码
