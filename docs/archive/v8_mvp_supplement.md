## 4. 配套说明一：预约状态机

### 4.1 状态定义

| 状态 | 说明 | 是否占用课时 |
|------|------|--------------|
| 未发布 | 管理员未发布排班 | 否 |
| 待预约 | 排班已发布，用户可提交预约 | 否 |
| 锁定中 | 用户提交预约，系统处理中（< 3 秒） | 否（即将预占） |
| 已预约 | 预约成功，课时已预占 | **是（预占 1 节）** |
| 候补中 | 满员时用户加入候补队列 | 否 |
| 被关注 | 用户关注该时段 | 否 |
| 上课中 | 课程进行中（开课前 15 分钟自动切换） | 是（仍为预占） |
| 待确认 | 课程结束，教练尚未点击确认 | 是（仍为预占） |
| 已完成 | 教练确认上课，预占 → 已扣 | **是（已扣 1 节）** |
| 已取消-学员主动 | 学员 24h 外取消 / 24h 内取消审批通过 | 否（已释放） |
| 已取消-教练请假 | 教练请假导致取消 | 否（已释放） |
| 已关闭-过期 | 时间段已过，未预约 / 未上课 | 否 |
| 已关闭-旷课确认 | 教练标记"未到课"，课时已扣 | 是（已扣） |

> 一对多相关状态（"已取消-人数不足"等）属 P2，本期不列出。

### 4.2 状态转移规则

```
[未发布]
  └─ 管理员发布排班 → [待预约]

[待预约]
  ├─ 用户点击预约 → [锁定中] → 成功 → [已预约]
  │                            → 失败（已被抢）→ [待预约]
  ├─ 用户候补（满员时）→ [候补中]
  ├─ 用户关注 → [被关注]
  └─ 时间到达，未被预约 → [已关闭-过期]

[已预约]
  ├─ 课程开始前 15 分钟 → [上课中]
  ├─ 学员 24h 外取消 → [已取消-学员主动]
  ├─ 学员 24h 内取消 + 教练通过 → [已取消-学员主动]
  ├─ 学员 24h 内取消 + 教练拒绝 → [已预约]（不变）
  ├─ 学员 24h 内取消 + 教练超时 → [已预约]（不变；决策 19）
  ├─ 教练请假 → [已取消-教练请假]
  └─ 课程时间到达 → [上课中]

[上课中]
  └─ 课程结束 → [待确认]

[待确认]
  ├─ 教练点击"确认上课" → [已完成]
  ├─ 教练超时（24h）未确认 → [已完成]（系统自动；决策 33）
  └─ 教练标记"学员未到课" → [已关闭-旷课确认]

[候补中]
  ├─ 有人取消 → 按候补顺序自动转正 → [已预约]
  └─ 候补有效期过期 → [已关闭-过期]
```

### 4.3 关键约束

1. **预占课时释放场景**（详见 §6.4）：24h 外取消 / 24h 内教练通过 / 特殊原因工单通过 / 教练请假。
2. **预占课时不释放场景**：24h 内教练拒绝 / 24h 内教练超时（视为拒绝）/ 旷课。
3. **超时自动扣除**：教练 24h 未确认上课，系统自动从"预占"转为"已扣"。
4. **状态扭转纪律**：已"已完成"或"已关闭-旷课确认"后，**不可**再回到"已预约"。退款只影响订单，不影响已扣课时。

## 5. 配套说明二：订单状态机

### 5.1 状态定义

| 状态 | 说明 |
|------|------|
| 待审批 | 订单已生成，教练待确认（针对需审批套餐） |
| 待用户确认 | 教练修改方案，待用户确认 |
| 已拒绝-教练 | 教练主动拒绝 |
| 已取消-超时 | 教练 24h 未处理 |
| 已取消-用户拒绝 | 用户拒绝教练修改方案 |
| 待支付 | 订单已确认，用户待支付 |
| 已关闭-超时未支付 | 订单 24h 未支付自动关闭 |
| 已关闭-用户取消 | 用户支付前主动取消 |
| 已支付-正常 | 一对一支付后，待上课 |
| 退款申请中 | 用户发起退款 |
| 退款审批中-教练 | 教练 24h 内审批 |
| 退款审批中-管理员 | 管理员 3 工作日内审批 |
| 争议退款处理中 | 客服介入 |
| 已退款 | 退款完成 |
| 已完成-已消耗 | 全部课时消耗完毕 |
| 已关闭-其他 | 其他异常关闭 |

> 固定搭档相关状态（"已支付-拼课中"等）属 P2，本期不列出。

### 5.2 状态转移规则

```
[待审批]
  ├─ 教练点击"确认"（未修改）→ [待支付]
  ├─ 教练点击"协商修改" → [待用户确认]
  ├─ 教练点击"拒绝" → [已拒绝-教练]
  └─ 24h 超时未处理 → [已取消-超时]

[待用户确认]
  ├─ 用户点击"确认支付" → [待支付]
  └─ 用户点击"拒绝" → [已取消-用户拒绝]

[待支付]
  ├─ 用户支付成功 → [已支付-正常]
  ├─ 用户主动取消 → [已关闭-用户取消]
  └─ 24h 超时未支付 → [已关闭-超时未支付]

[已支付-正常]
  ├─ 全部课时消耗完毕 → [已完成-已消耗]
  └─ 用户发起退款 → [退款申请中]

[退款申请中]
  ├─ 标准退款 → [退款审批中-教练]
  └─ 争议退款 → [争议退款处理中]

[退款审批中-教练]
  ├─ 教练同意 → [退款审批中-管理员]
  ├─ 教练拒绝 → [争议退款处理中]
  └─ 24h 超时 → [争议退款处理中]（视为拒绝）

[退款审批中-管理员]
  ├─ 同意 → [已退款]
  └─ 拒绝 → [已支付-正常]（课时不回滚）

[已退款]
  └─ 若该教练名下已无有效课时包 → 移除「学员」标签
```

### 5.3 关键约束

1. **订单与预约分离**：订单管支付，预约管上课。退款后对应预约状态同步取消。
2. **超时规则统一**：教练审批 24h、用户支付 24h、管理员退款 3 工作日。
3. **退款原路返回**：预计 3-7 工作日到账。
4. **争议退款可绕过教练**直接到客服。
5. **退款不自动撤销已消耗课时**：仅按"未消耗比例"计算退款金额（详见 §6.5）。

## 6. 配套说明三：课时预占 / 扣除 / 回滚模型

### 6.1 三种动作

| 动作 | 触发时机 | 数据变化 | 课时包状态 |
|------|----------|----------|------------|
| 预占 (Reserve) | 用户提交预约成功 | `reserved_count +1` | `reserved` |
| 扣除 (Deduct) | 教练确认上课 / 系统超时自动 / 教练标记旷课 | `reserved_count -1`，`consumed_count +1` | `consumed` |
| 释放 (Release) | 取消 / 请假 / 拼课失败 / 候补转正失败 | `reserved_count -1` | （预占被撤销） |

### 6.2 课时包字段

每个用户持有的有效套餐对应一个课时包对象：

| 字段 | 说明 |
|------|------|
| `package_id` | 课时包 ID |
| `user_id` | 用户 ID |
| `coach_id` | 绑定教练 ID |
| `total_hours` | 总课时 |
| `reserved_count` | 预占中（已预约未消耗） |
| `consumed_count` | 已消耗 |
| `available_count` | 可用 = `total_hours - reserved_count - consumed_count` |
| `expire_at` | 过期时间 |
| `purchased_at` | 购买时间 |
| `status` | `active` / `expired` / `refunded` |

**关键不变量**：`reserved_count + consumed_count + available_count = total_hours`，事务内校验。

### 6.3 扣减顺序规则

当用户拥有多个有效套餐时（如有历史未消耗套餐 + 新购套餐）：

- **默认顺序**：`expire_at` 升序 → 相同则 `purchased_at` 升序（FIFO）
- **预占时**：锁定在最早到期的套餐上
- **扣除时**：从预占所在的套餐扣除
- **管理员可调**：后台支持手动调整扣减优先级

> MVP 仅支持一个有效正价课时包（v7 决策 60），故"多套餐扣减顺序"仅在用户**历史过期**后再次购买时短暂存在。代码层面保留该逻辑。

### 6.4 回滚场景清单

| 场景 | 触发条件 | 预占 → 释放？ | 备注 |
|------|----------|---------------|------|
| 学员 24h 外主动取消 | 用户操作 | ✅ 释放 | — |
| 学员 24h 内取消 + 教练通过 | 教练审批 | ✅ 释放 | — |
| 学员 24h 内取消 + 教练拒绝 | 教练审批 | ❌ 保留 | 课时继续预占，课时仍可能后续扣除 |
| 学员 24h 内取消 + 教练超时 | 24h 无响应 | ❌ 保留 | 决策 19：默认拒绝 |
| 特殊原因取消 + 工单通过 | 客服审核 | ✅ 释放 | 学员需提供证明 |
| 特殊原因取消 + 工单拒绝 | 客服审核 | ❌ 保留 | 按旷课处理 |
| 教练请假 | 管理员审批 | ✅ 释放 | — |
| 候补转正失败（被他人抢走） | 系统并发 | ✅ 释放 | — |
| 学员旷课（教练标记） | 教练操作 | ❌ 不释放 → 直接扣除 | 决策 32 |
| 教练确认上课 | 教练操作 | ❌ 不释放 → 直接扣除 | — |
| 教练 24h 超时未确认 | 系统自动 | ❌ 不释放 → 自动扣除 | 决策 33 |
| 套餐过期 | 系统定时 | 全部 `reserved` → 释放；已 `consumed` 不变 | 过期即作废 |

### 6.5 退款与课时的关系

1. **未消耗课时**（`available + reserved`）：可退。
2. **已消耗课时**（`consumed`）：不可退。
3. **退款金额计算**：
   - 套餐价格 P，总课时 T，已消耗 C（含 reserved 已扣部分），可退金额 = `P × (T - C) / T`
4. **退款后课时包状态**：`status = refunded`，用户对该教练的「学员」标签移除。
5. **手续费**：MVP 阶段由客服手动判断，文档提示即可（v7 决策 4），不自动计算。

### 6.6 并发与一致性

1. **预占采用行级锁**：同一时段并发预约时，仅第一个事务成功。
2. **可用课时校验**：每次预占前校验 `available_count > 0`。
3. **失败回滚**：扣减失败 / 网络异常时，事务回滚，课时保持一致。
4. **幂等键**：支付回调使用订单号 + 操作类型作为幂等键，避免重复扣课时。

## 10. 争议退款 / 申诉兜底方案

> v7 §6.6 强依赖客服介入；v8 §3 把 4.6.7 客服工单系统挪到 P2。MVP 阶段必须有兜底方案，否则用户"投诉无门"。

### 10.1 兜底覆盖场景

| 场景 | 触发条件 | 兜底流程 |
|------|----------|----------|
| 教练 24h 内拒绝退款 | 教练在 [退款审批-教练] 状态点击拒绝 | 学员订单详情页出现「申请客服介入」按钮 → 进入 10.2 |
| 教练 24h 超时未审 | 系统定时扫描 | 自动转入 [争议退款处理中] → 通知学员 |
| 学员认为课时被多扣 | 学员在订单详情页提交申诉（原因 + 截图） | 进入 10.2 |
| 课程被取消后争议（教练请假 / 系统异常） | 学员主动联系 | 管理员微信群沟通后决定 → 后台处理 |
| **24h 内取消被教练拒绝** | **学员突发急事（疾病 / 事故等），24h 内取消申请被教练拒绝** | **学员在预约详情页提交"特殊原因申诉"（必填原因 + 证明材料）→ 进入 [争议退款处理中]，管理员 3 工作日内决定是否释放课时** |
| 实名认证审核不通过 | 管理员驳回 | 学员重新提交或联系客服微信群 |
| 套餐过期未消耗课时 | 学员发现过期 | 管理员手动决定是否补开或退款 |

### 10.2 争议退款处理流程

```
[学员发起申诉]
  ├─ 入口：订单详情页 / 预约详情页「申请客服介入」按钮
  │       触发条件：
  │         - 订单详情页：订单状态 ∈ { [已拒绝-教练], [已支付-正常](对课时有异议), [已退款](对结果有异议) }
  │         - 预约详情页：预约状态 = [已预约] 且 24h 内取消申请被教练拒绝（用于"特殊原因申诉"）
  ├─ 必填：申诉原因 + 截图（最多 5 张，每张 ≤ 5MB）
  │       「特殊原因申诉」需额外上传证明材料（医院证明 / 事故现场图等）
  └─ 提交后：进入 [争议退款处理中]（订单级与预约级申诉统一进入该状态）

[管理员处理]
  ├─ 入口：管理端「争议退款处理」页（§9.3 第 15 项）
  ├─ 必备信息：订单详情 + 学员申诉截图 + 教练意见（系统自动汇总）
  ├─ 决策：同意退款 / 拒绝 / 部分退款 / 调整课时
  └─ 时限：3 工作日内（与 v7 决策 27 一致）

[结果通知]
  ├─ 同意 → 订单进入 [退款审批中-管理员] → [已退款] → 通知学员
  ├─ 拒绝 → 订单回到 [已支付-正常]（或 [已关闭-其他]）→ 通知学员
  └─ 部分退款 → 课时包扣减 + 部分退款 → 通知学员
```

### 10.3 配套约束

1. **入口必须显著**：所有涉及教练拒绝 / 学员申诉的场景，订单详情页必须显示「申请客服介入」按钮。
2. **处理时限监控**：争议退款超过 3 工作日未处理 → 系统给管理员发催办通知 + 抄送超级管理员。
3. **微信群补充**：管理员可在企业微信群中先与学员初步沟通，达成一致后再在后台处理；沟通记录截图归档。
4. **P2 升级触发条件**：当争议量 > 5 条/日时，必须升级到工单系统（4.6.7）。

## 11. 签署时序 & 续费 / 过期流程

### 11.1 协议签署时序

| 时机 | 协议 | 是否强制 | 不签后果 |
|------|------|----------|----------|
| 微信授权登录成功 | 《隐私协议》 | ✅ 强制 | 弹窗拦截，无法进入首页 |
| 首次进入小程序（登录后） | 《用户须知》v1 | ✅ 强制 | 弹窗拦截，无法进入首页 |
| 首次购课 / 首次预约体验课前 | 《健康承诺书》 | ✅ 强制 | 购课按钮置灰，提示签署 |
| 首次购课 / 首次入场前 | 《免责协议》 | ✅ 强制 | 同上 |
| 《用户须知》更新后 | 《用户须知》新版本 | ✅ 强制（仅当版本号变化） | 下次购课弹窗拦截 |

**说明**：
- 注册时一次性弹 4 个，签署完成后下次仅《用户须知》更新时再弹。
- 签署记录保存至用户档案，关联签署时间与版本号，后台可查（v7 §7.3）。

### 11.2 续费流程

> 课时用完（学员标签移除）后，用户重新购买同一教练课时的流程。

| 步骤 | 系统行为 | 用户操作 |
|------|----------|----------|
| 1 | 移除学员标签，通知用户 | 用户进入"我的套餐"看到「已用完」+「续费」按钮 |
| 2 | 续费入口跳转至套餐购买页 | 默认带入原教练 + 上一份套餐的泳姿/人数/课时（可改） |
| 3 | 走 4.4.5 标准购课流程 | 选课时 → 提交订单 → 支付 |
| 4 | 支付成功 → 重新打上学员标签 | 通知用户续费成功 |

**续费 vs 新购的判定**：
- **续费**：同一教练，且上一份套餐已用完 / 已退款 / 已过期
- **新购**：更换教练（需先退原套餐，参见 v7 决策 42）

### 11.3 套餐过期流程

| 触发时机 | 系统行为 | 用户感知 |
|----------|----------|----------|
| 过期前 7 天 | 通知用户「套餐将于 X 天后过期，剩余 X 课时待使用」 | 微信订阅消息 + 应用内通知 |
| 过期前 3 天 | 同上 | 同上 |
| 过期前 1 天 | 同上 | 同上 |
| 过期当日 00:00 | 系统扫描：移除学员标签，释放全部预占课时 | 微信订阅消息 + 应用内通知 |
| 过期后 | 用户进入"我的套餐"看到「已过期」+「续费」按钮 | UI 明确显示 |

**已预占但未消耗的处理**：
- 套餐过期前，已预占的预约（已预约 / 上课中 / 待确认）→ 通知用户改约或保留
- 改约：在其他有效套餐或新购套餐上完成
- 保留：特殊情况下由管理员手动延期（不推荐自动化）

### 11.4 异常情况兜底

| 场景 | 处理 |
|------|------|
| 套餐过期前用户未消费任何课时 | 通知 + 续费入口 |
| 套餐过期前仍有未消耗预约 | 通知 + 改约 / 保留 |
| 套餐过期 + 用户申请退款 | 走争议退款（§10） |
| 用户同时持有多份套餐（历史遗留） | 按 §6.3 顺序过期 |
