### US-041 管理员处理教练离职

- **当前 INDEX 状态**：[REVIEW]
- **综合评分**：6.5 / 10
- **维度评分表**

| 维度 | 评分 | 说明 |
|------|------|------|
| 产品设计合理性 | 7/10 | 审批队列 + checklist + 批量变更的页面路径清晰；但“通过即自动生成退款记录”把多选项业务压缩为单一退款，设计路径偏窄。 |
| 业务逻辑 | 5/10 | checklist 与 PRD §5.5.1.1 不一致；退款金额公式与 PRD §6.4.2 不一致；自动退款逻辑与 PRD “可转新教练/继续上完” 冲突。 |
| Figma 可设计性 | 7/10 | 队列、详情、弹窗、checklist 四态已列，但批量变更结果反馈需额外设计 loading/失败态。 |
| 泳道/角色完整性 | 7/10 | 管理员、系统行为完整；学员/教练仅作为被动影响方，未在泳道中体现“选择转教练/继续上课”的主动分支。 |
| 异常场景 | 7/10 | 5 个 GWT 场景覆盖权限、checklist、排班、状态；但场景 1 的 Given 未覆盖 `active 学员数 = 0` 分支。 |
| 商业合规 | 6/10 | 100% 退款硬约束被引用，但执行方式（自动全部生成退款记录）偏离 PRD 的“学员申请/管理员安排”双通道，存在合规口径风险。 |

- **主要问题**
  - 🔴 **位置**：`user-story.md §4.1 第 49-53 行`
    **问题**：checklist 写为“① active 学员数 = 0；② 若 active 学员数 > 0，所有 active 套餐已确认全额退款”，但 PRD §5.5.1.1 第 590-594 行要求“① active 学员数 = 0；② 所有学员处理结果已登记”，并明确每个学员可“转新教练 / 全额退款 / 继续上完”。US 把三选一压缩为只能全额退款，排除了转教练和继续上课两种合法结果。
    **建议**：恢复 PRD 的“学员处理结果已登记”checklist，并在详情页展示每份 active 套餐的处理结果（转教练 / 退款 / 继续上课），通过后端校验至少有一种结果登记。

  - 🔴 **位置**：`user-story.md §4.1 第 56 行`
    **问题**：审批通过后“对所有 active package（含未确认退款的套餐），系统自动生成 100% 待退款记录 `refund_amount = 单价 × 剩余课时`”。这与 PRD §5.5.1.1 第 577 行“管理员可为受影响学员安排其他教练承接剩余课时，或按退款流程处理”直接冲突；且 PRD §6.4.5 第 940 行明确 coach_resigned 的 100% 退款是在学员申请退款时触发，非系统自动生成。
    **建议**：审批通过时不应自动为所有 package 生成退款记录，仅对管理员/学员已选择“全额退款”的 package 生成；选择“转新教练”的 package 应在 US-022 流程中转为主动状态。

  - 🔴 **位置**：`user-story.md §4.1 第 56 行 / §6.1 第 100 行`
    **问题**：退款金额使用“单价 × 剩余课时”，而 PRD §6.4.2 第 867 行公式为 `可退金额 = paid_amount × (total_hours - consumed_count) / total_hours`。若存在折扣、赠课或自定义套餐，`单价` 与 `paid_amount / total_hours` 可能不一致，导致金额偏差。
    **建议**：统一使用 PRD §6.4.2 公式，以 `paid_amount` 和 `consumed_count` 为计算基准；单价仅作为展示参考。

  - 🟡 **位置**：`user-story.md §4.1 第 57 行`
    **问题**：取消未来 booking 的状态范围写为“status ∈ 已预约/待上课”，但 PRD §5.5.1.1 第 599 行 SQL 为 `status IN ('已预约', '待支付', '待上课')`，遗漏了“待支付”状态。
    **建议**：补全为 `status IN ('待支付', '已预约', '待上课')`，与 PRD 一致。

  - 🟡 **位置**：`user-story.md §6.1 第 95-97 行`
    **问题**：场景 1 的 Given 同时给出“active 学员数 > 0”和“3 份 active 套餐均已确认全额退款”，未覆盖“active 学员数 = 0”这一更简单的通过分支，导致 checklist 分支覆盖不全。
    **建议**：拆分两个正常场景：a) active 学员数 = 0；b) active 学员数 > 0 但每份套餐已登记处理结果。

- **推荐状态**：[REVIEW]（不变），但需修复上述 P0 后方可进入 [APPROVED]。
- **Figma 准备度**：⚠️ 需补充“学员处理结果登记”交互（转教练/退款/继续上课）后方可进入；当前 placeholder 不足以覆盖 PRD 三选一逻辑。
