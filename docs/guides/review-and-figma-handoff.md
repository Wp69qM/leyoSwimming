## 2. 评审与定稿要做什么？

评审与定稿 = 把 US 从 `[REVIEW]` 推进到 `[APPROVED]`。

### 2.1 业务评审（PM / 业务负责人）

逐份检查 `docs/stories/US-XXX-.../user-story.md`：

| 检查项 | 关注点 |
|--------|--------|
| 业务准确性 | 流程、规则、数值是否与 PRD 一致 |
| Gherkin 场景 | 正常/异常路径是否覆盖完整，Then 是否有具体断言 |
| 边界场景 | 至少 3 个异常是否真实存在 |
| 依赖关系 | 前置 US、后续 US 是否画得对 |
| 角色术语 | 是否仅使用「学员/教练/管理员/系统/游客」 |
| 命名规范 | 标题是否为 `[角色]+[动作]+[目标]` |

### 2.2 设计评审（设计师）

- 根据 `user-story.md` §13 的 Figma 占位，产出 Figma 原型
- 在 `user-story.md` §15 填写评审记录（评审人/反馈/处置）
- 补充 §13 的 Figma file URL、frame 名称、状态截图清单
- 每个页面必须覆盖 **空 / 加载 / 错误 / 成功** 四态

### 2.3 技术预审（开发负责人，可选）

- 快速扫 `tech-design.md` 确认 API/数据模型/状态机无重大遗漏
- 但不展开实现，那是 TDD 阶段的事

### 2.4 更新状态

全部通过后，把 `docs/spec/user-story/INDEX.md` 中对应 US 的状态改为 `[APPROVED]`。

## 3. 故事逻辑能串成完整页面吗？

能。50 个 US 不是孤立的，而是按 **用户旅程 + 角色端** 组织成多条主线：

| 主线/端 | 涉及 US | 串成的核心页面 |
|--------|---------|---------------|
| 游客浏览 → 注册登录 | US-001~US-009 | 启动页、首页、场馆公告、教练列表、教练详情、微信授权、补充手机号、登录、安全设置 |
| 体验课转化 | US-017~US-018 | 套餐列表、套餐详情、订单确认、支付、预约 |
| 正价套餐购买 | US-019~US-022, US-025~US-028 | 套餐浏览、购买、支付、订单列表/详情、退款 |
| 上课闭环 | US-029~US-034, US-036 | 我的预约、预约详情、签到、上课记录 |
| 教练端 | US-010~US-014, US-036~US-040 | 入驻、主页管理、排班、请假、离职、重新入驻 |
| 管理后台 | US-015~US-016, US-041~US-049 | 教练审核、离职处理、用户/订单/套餐管理、场馆配置、数据看板 |

## 5. 什么叫「Figma 原型的每页四态」？

「四态」是指 **每个页面都必须设计 4 种 UI 状态**，确保上线后用户在任何情况下都有明确反馈：

| 状态 | 含义 | 示例 |
|------|------|------|
| **空状态（Empty）** | 没有数据时页面长什么样 | 我的预约页：「暂无预约，去约课吧」+ 空插图 |
| **加载状态（Loading）** | 等待网络/接口响应时 | 教练列表页：骨架屏或 Loading 徽标 |
| **错误状态（Error）** | 请求失败或操作被拒时 | 支付页：「支付失败，请重试」+ 错误码 |
| **成功状态（Success）** | 操作成功后的确认/结果页 | 预约成功页：「预约成功」+ 日历入口 |

### 为什么必须四态？

这是 AGENTS.md §5.2 的硬约束：

> UI（设计）：设计稿覆盖空 / 加载 / 错误 / 成功 四种状态。

四态不全 → 开发时容易漏掉异常分支 → 上线后用户遇到白屏/卡死/无反馈。

## 6. 下一步推荐动作

### Step 1：PM 先做业务评审

- 通读 `docs/spec/user-story/INDEX.md`
- 按能力分组逐份阅读 `docs/stories/US-XXX-.../user-story.md`
- 记录问题，修改文档

### Step 2：设计负责人先填 L1 全局规范

在把具体 US 交给设计师之前，先完善 [docs/figma/README.md](../../../docs/figma/README.md)：

- 颜色 / 字体 / 间距 Token
- 组件库来源与引用方式
- 状态徽标视觉定义
- 4 态模板

> L1 层一次定义，所有 US 共享。必须先定，否则每个 US 的设计师会各做一套。

### Step 3：按页面/流程分组打包 US

不要直接扔 50 个 US 给设计师。建议按 **页面** 或 **流程** 分组，例如：

**包 1：用户端首页 → 教练详情**
- US-001 游客浏览教练列表与详情
- US-002 游客查看套餐、公告与场馆信息
- US-003 游客查看预约释放倒计时

**包 2：用户端购买 → 支付 → 订单**
- US-019 学员浏览正价套餐
- US-020 学员购买正价套餐
- US-025 学员支付套餐订单
- US-026 学员查看订单列表与详情

**包 3：教练端入驻与主页**
- US-010 教练提交入驻资料
- US-011 管理员审核教练入驻资质
- US-012 教练管理个人主页与参考单价
- US-038 教练分享个人主页与可约时段

以此类推。

### Step 4：设计师读取指定文件

| 文件 | 用途 | 是否必须 |
|------|------|---------|
| `docs/prd/prd.md` | 理解全局业务与页面清单 | ✅ |
| `docs/figma/README.md` | 全局设计系统、Token、组件、徽标 | ✅ |
| `docs/spec/user-story/INDEX.md` | 了解 US 分组、依赖、状态机 | ✅ |
| `docs/stories/US-XXX-.../user-story.md` | **核心输入**：业务目标、触发条件、流程、GWT、页面级设计决策 | ✅ |
| `docs/stories/US-XXX-.../tech-design.md` | 辅助参考数据字段、状态值 | 可选 |

> 设计师**重点读 `user-story.md` 的 §1-§6（业务）和 §13-§15（Figma 相关）**。

### Step 5：设计师产出 Figma 原型

每个页面产出 **空 / 加载 / 错误 / 成功** 四态。

### Step 6：回填 Figma 链接与评审记录

- PM/开发负责人把 Figma file URL、frame 名填入每个 US 的 `user-story.md` §13
- 在 §15 记录设计评审结论
- 把 `INDEX.md` 中对应 US 状态改为 `[APPROVED]`

### Step 7：进入 TDD 实现

全部 `[APPROVED]` 后，按 AGENTS.md 调用 `test-driven-development` skill 开始编码。
