## 4. 业务流程

### 4.1 主路径

1. 用户进入「我的 → 注销账号」页面
2. 系统展示注销风险提示，内容包括但不限于：
   - 注销后账号不可找回，原账号内的头像、昵称、个人资料、历史订单、套餐、教练关系等数据将与新账号隔离
   - 注销后用户使用同一手机号/微信重新登录，将视为新用户重新注册，不绑定原账号数据
   - 注销后 90 天内历史订单/交易记录仍会保留，超期后匿名化处理
3. 系统以 checklist 形式展示需满足条件：
   - 无 active 状态的套餐
   - 无未完成订单（待支付/待确认/退款中）
   - 无进行中或待上课的预约/课程
4. 系统校验上述条件全部满足
5. 用户点击「确认注销」
6. 系统弹出二次确认弹窗，再次提示「注销后账号不可找回，是否确认注销？」
7. 用户点击弹窗「确认」
8. 系统将账号标记为软删除状态，`user.status = 1`（PRD §9.2.1：0=正常 1=软删除 2=封禁），并记录 `deleted_at`
9. 系统执行注销后数据保留策略：订单/套餐历史保留 90 天，超期匿名化（PRD §3.7、§5.2.1、附录 D45）
10. 系统清除登录态，跳转至登录页

### 4.2 异常分支

- **分支 1**：存在 active 套餐 → 提示「您还有未完成的套餐，无法注销」
- **分支 2**：存在未完成订单 → 提示「您有未完成订单，请完成后注销」
- **分支 3**：存在进行中或待上课的预约/课程 → 提示「您有未完成的课程预约，请完成后注销」
- **分支 4**：用户在二次确认弹窗中点击「取消」→ 停留在注销账号页面，不执行注销
- **分支 5**：已注销账号再次登录 → 视为新用户，重新注册

## 6. 验收标准（业务级 Gherkin）

### 6.1 场景 1：正常注销账号

```gherkin
Given 用户已登录且无 active 套餐、无未完成订单、无进行中预约
And   用户已进入「我的 → 注销账号」页面
When  系统展示注销风险提示与需满足条件 checklist
And   用户查看 checklist 全部通过
And   用户点击「确认注销」
And   系统在二次确认弹窗中提示「注销后账号不可找回，是否确认注销？」
And   用户点击「确认」
Then  user.status = 1（软删除）
And   user.deleted_at 等于当前时间
And   登录态被清除
And   页面跳转至登录页
And   历史订单数据保留 90 天
```

### 6.2 场景 2：存在 active 套餐时注销

```gherkin
Given 用户已登录且存在 active 套餐
When  用户进入「我的 → 注销账号」页面
Then  需满足条件 checklist 中「无活跃套餐」显示为未通过
And   「确认注销」按钮置灰不可点击
And   前端提示"您还有未完成的套餐，无法注销"
And   user.status 保持 0（正常）
```

### 6.3 场景 3：存在未完成订单时注销

```gherkin
Given 用户已登录且存在待支付订单
When  用户进入「我的 → 注销账号」页面
Then  需满足条件 checklist 中「无未完成订单」显示为未通过
And   「确认注销」按钮置灰不可点击
And   前端提示"您有未完成订单，请完成后注销"
And   user.status 保持 0（正常）
```

### 6.4 场景 4：存在进行中预约时注销

```gherkin
Given 用户已登录且存在待上课的课程预约
When  用户进入「我的 → 注销账号」页面
Then  需满足条件 checklist 中「无进行中预约」显示为未通过
And   「确认注销」按钮置灰不可点击
And   前端提示"您有未完成的课程预约，请完成后注销"
And   user.status 保持 0（正常）
```

### 6.5 场景 5：用户在二次确认弹窗中取消

```gherkin
Given 用户已满足所有注销条件
When  用户点击「确认注销」
And   系统在二次确认弹窗中提示「注销后账号不可找回，是否确认注销？」
And   用户点击「取消」
Then  弹窗关闭
And   用户停留在注销账号页面
And   user.status 保持 0（正常）
```

## 8. 边界场景

### 8.1 边界场景 1：重复提交注销

- **触发条件**：用户快速点击两次「确认注销」
- **预期行为**：幂等处理，第二次返回已注销结果
- **用户可见反馈**：正常跳转登录页

### 8.2 边界场景 2：注销后使用原手机号重新注册

- **触发条件**：注销后 90 天内用户使用原手机号登录
- **预期行为**：系统视为新用户，创建新 user 记录，原数据不关联
- **用户可见反馈**：进入资料补充页/登录成功提示

### 8.3 边界场景 3：注销过程中新增预约

- **触发条件**：用户在校验通过到确认注销之间新增预约
- **预期行为**：最终提交时重新校验，如有 active 预约则拒绝
- **用户可见反馈**："注销条件已变化，请重新检查"

## 14. 页面级设计决策

### 14.1 注销条件前置展示

- **背景**：用户可能不清楚为何不能注销
- **选项**：A. 提交后才报错；B. 进入页面即展示条件 checklist
- **结论**：选择 B，用 checklist 形式展示 active 套餐、未完成订单、进行中预约等状态
- **影响范围**：注销确认页 UI

### 14.2 注销风险提示展示

- **背景**：注销是高风险操作，需明确告知用户后果
- **选项**：A. 仅简单文案；B. 结构化风险提示卡片 + 关键后果高亮
- **结论**：选择 B，展示账号不可找回、数据隔离、重新注册不绑定原数据、90 天后匿名化等关键信息
- **影响范围**：注销确认页 UI

### 14.3 二次确认方式（MVP 简化）

- **背景**：防止误操作和恶意注销
- **选项**：A. 登录密码；B. 短信验证码；C. 弹窗确认/取消（MVP 简化）
- **结论**：选择 C。MVP 阶段仅使用弹窗二次确认，点击「确认」后执行注销，点击「取消」则关闭弹窗。短信验证码/密码校验可在后续版本增强
- **影响范围**：注销确认流程、二次确认弹窗 UI

### 14.4 页面级交互说明

| 交互 | 触发 | 反馈 | 备注 |
|------|------|------|------|
| 进入注销页 | 页面加载 | 展示风险提示 + 条件 checklist | 条件不满足时「确认注销」按钮置灰 |
| 条件 checklist 全部通过 | 自动校验完成 | 「确认注销」按钮高亮可点击 | — |
| 点击「确认注销」 | 按钮点击 | 弹出二次确认弹窗 | 弹窗文案「注销后账号不可找回，是否确认注销？」 |
| 弹窗点击「确认」 | 弹窗按钮 | 执行注销，清除登录态，跳转登录页 | — |
| 弹窗点击「取消」 | 弹窗按钮 | 关闭弹窗，停留在注销页 | — |
| 条件变化 | 后台检测到不满足 | 按钮禁用 + 提示 | 实时或提交时校验 |
