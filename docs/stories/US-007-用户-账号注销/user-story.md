---

## 4. 业务流程

### 4.1 主路径

1. 用户进入注销账号页面
2. 系统展示注销风险提示与需满足条件
3. 系统校验：无 active 套餐、无未完成订单
4. 用户输入登录密码或验证码进行二次确认
5. 用户勾选「已阅读注销协议」并点击「确认注销」
6. 系统将账号标记为注销状态，`user.status = 2`
7. 系统清除登录态，跳转至登录页

### 4.2 异常分支

- **分支 1**：存在 active 套餐 → 提示「您还有未完成的套餐，无法注销」
- **分支 2**：存在未完成订单 → 提示「您有未完成订单，请完成后注销」
- **分支 3**：二次确认失败 → 提示「验证失败，请重新验证」
- **分支 4**：已注销账号再次登录 → 视为新用户，重新注册

## 6. 验收标准（业务级 Gherkin）

### 6.1 场景 1：正常注销账号

```gherkin
Given 用户已登录且无 active 套餐、无未完成订单
When  用户完成二次确认并点击「确认注销」
Then  user.status = 2（已注销）
And   登录态被清除
And   页面跳转至登录页
And   历史订单数据保留 90 天
```

### 6.2 场景 2：存在 active 套餐时注销

```gherkin
Given 用户已登录且存在 active 套餐
When  用户尝试注销账号
Then  返回错误码 ACTIVE_PACKAGE_EXISTS
And   前端提示"您还有未完成的套餐，无法注销"
And   user.status 保持 1（正常）
```

### 6.3 场景 3：存在未完成订单时注销

```gherkin
Given 用户已登录且存在待支付订单
When  用户尝试注销账号
Then  返回错误码 PENDING_ORDER_EXISTS
And   前端提示"您有未完成订单，请完成后注销"
And   user.status 保持 1（正常）
```

## 8. 边界场景

### 8.1 边界场景 1：重复提交注销

- **触发条件**：用户快速点击两次「确认注销」
- **预期行为**：幂等处理，第二次返回已注销结果
- **用户可见反馈**：正常跳转登录页

### 8.2 边界场景 2：注销后使用原手机号重新注册

- **触发条件**：注销后 90 天内用户使用原手机号登录
- **预期行为**：系统视为新用户，创建新 user 记录，原数据不关联
- **用户可见反馈**：进入资料补充页/登录成功提示

### 8.3 边界场景 3：注销过程中新增预约

- **触发条件**：用户在校验通过到确认注销之间新增预约
- **预期行为**：最终提交时重新校验，如有 active 预约则拒绝
- **用户可见反馈**："注销条件已变化，请重新检查"

## 14. 页面级设计决策

### 14.1 注销条件前置展示

- **背景**：用户可能不清楚为何不能注销
- **选项**：A. 提交后才报错；B. 进入页面即展示条件 checklist
- **结论**：选择 B，用 checklist 形式展示 active 套餐、未完成订单等状态
- **影响范围**：注销确认页 UI

### 14.2 页面级交互说明

| 交互 | 触发 | 反馈 | 备注 |
|------|------|------|------|
| 确认注销 | 点击按钮 | 二次确认弹窗 | 弹窗需再次输入密码/验证码 |
| 条件变化 | 后台检测到不满足 | 按钮禁用 + 提示 | 实时或提交时校验 |
