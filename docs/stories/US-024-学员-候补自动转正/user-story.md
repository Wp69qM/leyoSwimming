- **触发方**：系统

- **触发时机**：其他学员/教练取消预约后即时触发

## 3. 前置条件

- [x] 目标时段存在 status=waiting 的 waitlist 记录（依赖 US-023）
- [x] 候补学员仍持有 active 套餐且 available > 0
- [x] 目标时段仍处于可预约状态

---

## 4. 业务流程

### 4.1 主路径

1. 系统监听到 booking 取消事件（schedule_slot 释放 1 个名额）
2. 系统查询该 slot 下最早的 waiting waitlist 记录
3. 系统校验该用户身份、active 套餐、available > 0
4. 系统创建 booking 记录（status=已预约）
5. 系统从最早 active 套餐中预占 1 课时（available -1，reserved +1）
6. 系统将 waitlist.status 更新为 converted
7. 系统取消该用户其他 waiting 状态的 waitlist（按 §5.3.2 规则）
8. 系统向转正学员发送预约成功通知
9. 系统向该 slot 的关注用户发送「时段可约/已释放」提醒

### 4.2 异常分支

- **分支 1**：首位候补学员无可用课时 → 跳过该学员，继续检查下一位
- **分支 2**：首位候补学员已取消 waitlist → 跳过，继续检查下一位
- **分支 3**：无 waitlist → 仅发送关注提醒，不创建 booking

## 6. 验收标准（业务级 Gherkin）

### 6.1 场景 1：取消后首位候补转正

```gherkin
Given 教练 A 明日 9:00 时段已有 1 条 booking
And   学员 X 排队候补该时段（waitlist.status=waiting）
And   学员 X 持有 active 套餐且 available=3
When  原预约学员取消该 booking
Then  系统自动为学员 X 创建 booking.status = 已预约
And   学员 X 套餐 available=2，reserved=1
And   waitlist.status = converted
And   系统向学员 X 发送预约成功通知
And   系统向关注该时段的用户发送提醒
```

### 6.2 场景 2：多人候补仅首位转正

```gherkin
Given 教练 A 明日 9:00 时段释放 1 个名额
And   waitlist 顺序为：学员 X（第1）、学员 Y（第2）
And   两人均持有 active 套餐且 available > 0
When  系统处理候补转正
Then  仅学员 X 被自动预约
And   学员 Y 保持 waiting 状态
```

### 6.3 场景 3：首位候补无可用课时

```gherkin
Given 教练 A 明日 9:00 时段释放 1 个名额
And   首位候补学员 X 的 active 套餐 available=0
And   次位候补学员 Y 的 active 套餐 available=2
When  系统处理候补转正
Then  跳过学员 X，为学员 Y 创建 booking
And   学员 Y 的 waitlist.status = converted
And   学员 X 的 waitlist 保持 waiting
```

### 6.4 场景 4：首位候补已取消

```gherkin
Given 教练 A 明日 9:00 时段释放 1 个名额
And   首位候补学员 X 的 waitlist.status = cancelled
And   次位候补学员 Y 的 waitlist.status = waiting
When  系统处理候补转正
Then  跳过学员 X，为学员 Y 创建 booking
```

### 6.5 场景 5：无候补仅触发关注提醒

```gherkin
Given 教练 A 明日 9:00 时段释放 1 个名额
And   该时段无任何 waitlist 记录
And   用户 Z 关注了该时段
When  系统处理取消事件
Then  不创建 booking
And   向用户 Z 发送「时段可约」提醒
```

## 7. 数据/API/状态机影响

### 7.1 数据表影响

| # | 表名 | 操作 | 说明 |
|---|------|------|------|
| 1 | `booking` | 新增 | 自动预约记录 |
| 2 | `package` | 修改 | available -1，reserved +1 |
| 3 | `waitlist` | 修改 | converted / cancelled |

### 7.2 API 影响

（本 US 为事件驱动，无新增用户端 API；内部服务消费 booking 取消事件）

### 7.3 状态机影响

| # | 实体 | 转换 | 触发条件 | 说明 |
|---|------|------|---------|------|
| 1 | `waitlist` | waiting → converted | 自动转正成功 | — |
| 2 | `waitlist` | waiting → cancelled | 用户其他 waitlist 转正 | — |
| 3 | `package` | available → reserved | 自动预占课时 | §6.3.1 |
| 4 | `booking` | 无 → 已预约 | 自动转正 | — |

## 8. 边界场景

### 8.1 边界场景 1：并发取消与候补加入

- **触发条件**：取消事件触发转正的同时，新用户加入候补
- **预期行为**：事务控制保证名额不超额，新加入者按顺序排在后面
- **用户可见反馈**：排队位置正确

### 8.2 边界场景 2：用户多个 waitlist 同时触发

- **触发条件**：用户同时排在多个 slot 的第一位，且多个 slot 同时释放名额
- **预期行为**：只转正一个 slot，其余自动 cancelled
- **用户可见反馈**：仅收到一条预约成功通知，其余候补被取消通知

### 8.3 边界场景 3：关注用户与候补用户为同一人

- **触发条件**：学员 X 既候补又关注了同一 slot
- **预期行为**：转正后不再重复发送关注提醒
- **用户可见反馈**：仅收到预约成功通知

## 12. 备注

- **性能要求**：候补转正处理 P99 < 300ms
