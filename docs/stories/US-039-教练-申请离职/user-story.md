## 2. 触发条件

- **触发方**：教练
- **触发动作**：在教练端「我的 → 申请离职」提交申请，并对名下 active 学员套餐确认全额退款
- **触发时机**：用户主动操作

---

## 3. 前置条件

- [x] 教练已登录且 `coach.status = 1`（已通过入驻审核，依赖 US-011 / US-012）
- [x] 教练端已开通「申请离职」入口（status=1 可见）
- [x] 系统已存在该教练的 active 套餐或 booking 数据（用于生成学员清单）

---

## 4. 业务流程

### 4.1 主路径

1. 教练进入「我的 → 申请离职」
2. 系统校验 `coach.status = 1`
3. 教练选填离职原因（非必填）
4. 教练提交申请
5. 系统将 `coach.status` 从 1 更新为 4（申请中）
6. 系统生成「离职工单」，列出该教练所有 active 学员套餐：学号、姓名、剩余课时、单价
7. 教练在工单中对每份 active 套餐确认「全额退款」处理结果并落库：登记 `action='refund'`，系统自动生成 100% 退款记录 `refund_amount = 单价 × 剩余课时`（已消耗课时不退）。未确认套餐默认按「全额退款」处理，系统同步生成待退款记录。
8. 教练确认处理结果后，将工单提交至管理员审批队列

### 4.2 异常分支

- **分支 1**：教练状态非 1 → 入口隐藏，点击时提示「当前状态不可申请离职」
- **分支 2**：教练已处于 status=4 → 提示「您已提交离职申请，请在工单中查看进度」
- **分支 3**：教练尝试登记非自己名下套餐的处理结果 → 返回错误 `NOT_OWN_PACKAGE`

## 6. 验收标准（业务级 Gherkin）

> 本 US 为 L2（1 人天），包含 2 个正常场景 + 3 个异常场景 = 5 个场景。

### 6.1 场景 1：教练成功提交离职申请

```gherkin
Given 教练 C 已登录且 coach.status = 1
And   教练 C 名下有 3 份 active 套餐
When  教练 C 填写离职原因="个人发展"并提交申请
Then  coach.status 更新为 4（申请中）
And   系统生成 1 条离职工单 ticket.status = "processing"
And   工单中学员清单包含 3 份套餐及其剩余课时
And   返回 HTTP 200 与提示"离职申请已提交，请处理学员套餐"
```

### 6.2 场景 2：教练确认学员套餐全额退款

```gherkin
Given 教练 C 的离职工单已生成
And   学员 S 的 package P1（active，剩余 5 课时，单价 300 元）在工单中
When  教练 C 确认对 P1 的处理结果="全额退款"
And   点击保存
Then  coach_resignation_action 表新增 1 条记录
And   action='refund'、status='registered'
And   系统自动生成 100% 退款记录 refund_amount = 300 × 5 = 1500 元
And   工单进度更新为"1 / 3 已确认"
```

### 6.3 场景 3：非已通过教练无法申请离职

```gherkin
Given 教练 C 的 coach.status = 0（待审核）
When  教练 C 访问「申请离职」入口
Then  入口隐藏或按钮置灰
And   提示"入驻审核通过后可申请离职"
```

### 6.4 场景 4：重复提交离职申请

```gherkin
Given 教练 C 的 coach.status = 4（申请中）
When  教练 C 再次调用提交离职申请接口
Then  返回错误码 RESIGNATION_ALREADY_PENDING
And   HTTP 状态码 409
And   coach.status 保持 4，不生成新工单
```

### 6.5 场景 5：教练登记非自己名下套餐

```gherkin
Given 教练 C 的离职工单已生成
And   package P2 不属于教练 C
When  教练 C 对 P2 提交处理结果="全额退款"
Then  返回错误码 NOT_OWN_PACKAGE
And   HTTP 状态码 403
And   coach_resignation_action 表不写入记录
```

## 8. 边界场景

### 8.1 边界场景 1：教练在管理员审批前撤销离职申请

- **触发条件**：教练提交申请后、管理员审批前，希望继续教学
- **说明**：PRD §5.4.7 未定义撤销离职申请流程；MVP 暂不支持该操作，后续如需支持需先在 PRD 中补充 `4 → 1` 状态转换与审批队列处理规则
- **预期行为（当前 MVP）**：教练端不展示「撤销申请」入口；如需撤销，需联系管理员在 US-041 中驳回（PRD 未定义，亦不支持）
- **用户可见反馈**：无撤销入口，或提示「离职申请提交后不可自行撤销」

### 8.2 边界场景 2：教练名下无 active 套餐

- **触发条件**：教练提交离职申请时名下没有 active 套餐
- **预期行为**：系统仍允许提交，工单学员清单为空，可直接提交至管理员审批
- **用户可见反馈**：工单显示「无待处理学员套餐」

### 8.3 边界场景 3：并发提交离职申请

- **触发条件**：教练快速多次点击提交
- **预期行为**：使用幂等键去重，仅生成 1 张工单
- **用户可见反馈**：仅一次成功提示

## 12. 备注

- **幂等键**：`Idempotency-Key: coach:{coach_id}:resignation:apply`
- **事务边界**：coach.status 更新 + 工单创建在同一事务
- **退款硬约束**：教练主动离职时，按 PRD §5.4.7 三选一处理；action=refund 时 `refund_amount = price_per_hour × (reserved_count + available_count)`（PRD §6.4.5，已消耗课时不退）
- **三选一处理**：MVP 阶段 active 套餐允许「转新教练 / 全额退款 / 继续上完」三选一（PRD §5.4.7），由教练与学员私下沟通后登记
- **默认退款**：工单提交时未确认处理结果的 active 套餐，系统自动按「全额退款」生成待退款记录
- **性能要求**：提交接口 P99 < 300ms，工单详情 P99 < 200ms
- **隐私**：status=4 期间不 push 通知学员，教练列表/搜索不展示「申请中」标签
- **撤销限制**：MVP 不支持教练自行撤销离职申请；PRD §5.4.7 未定义 `4 → 1` 转换，避免状态机断裂

## 14. 页面级设计决策

### 14.1 离职入口可见性

- **背景**：status=4 期间需要强隐私，不能暴露「申请中」标签
- **选项**：A. 所有状态教练均可见入口；B. 仅 status=1 可见
- **结论**：选择 B，避免待审核/已离职教练误操作
- **影响范围**：教练端「我的」页面

### 14.2 工单中套餐处理选项

- **背景**：需要让教练登记每份 active 套餐的后续安排，同时符合项目硬约束
- **选项**：A. 允许「转新教练 / 全额退款 / 继续上完」；B. 仅允许「全额退款」
- **结论**：选择 A，按 PRD §5.4.7 三选一执行（转新教练 / 全额退款 / 继续上完，每份 active 套餐独立处理）
- **影响范围**：离职工单处理页展示三选一操作，coach_resignation_action.action 支持 refund/transfer/continue

### 14.3 页面级交互说明

| 交互 | 触发 | 反馈 | 备注 |
|------|------|------|------|
| 进入申请离职 | 点击菜单 | 弹出确认弹窗 | 提示处理完学员后再提交 |
| 提交申请 | 确认提交 | 跳转工单页 | status 变为 4 |
| 确认退款 | 点击套餐行 | 展示退款金额与确认按钮 | 金额 = 单价 × 剩余课时 |
| 提交至管理员 | 点击按钮 | 提示"已提交审核" | 工单进入 pending_audit |
