## 2. 触发条件

- **触发方**：教练
- **触发动作**：在教练端「我的 → 申请离职」提交申请，并对名下 active 学员套餐登记处理结果
- **触发时机**：用户主动操作

---

## 3. 前置条件

- [x] 教练已登录且 `coach.status = 1`（已通过入驻审核，依赖 US-011 / US-012）
- [x] 教练端已开通「申请离职」入口（status=1 可见）
- [x] 系统已存在该教练的 active 套餐或 booking 数据（用于生成学员清单）

---

## 4. 业务流程

### 4.1 主路径

1. 教练进入「我的 → 申请离职」
2. 系统校验 `coach.status = 1`
3. 教练选填离职原因（非必填）
4. 教练提交申请
5. 系统将 `coach.status` 从 1 更新为 4（申请中）
6. 系统生成「离职工单」，列出该教练所有 active 学员套餐：学号、姓名、剩余课时
7. 教练私下与学员沟通后，在工单中对每份 active 套餐登记处理结果：转新教练 / 全额退款 / 继续上完
8. 教练确认处理结果后，将工单提交至管理员审批队列

### 4.2 异常分支

- **分支 1**：教练状态非 1 → 入口隐藏，点击时提示「当前状态不可申请离职」
- **分支 2**：教练已处于 status=4 → 提示「您已提交离职申请，请在工单中查看进度」
- **分支 3**：教练尝试登记非自己名下套餐的处理结果 → 返回错误 `NOT_OWN_PACKAGE`

## 6. 验收标准（业务级 Gherkin）

> 本 US 为 L2（1 人天），包含 2 个正常场景 + 3 个异常场景 = 5 个场景。

### 6.1 场景 1：教练成功提交离职申请

```gherkin
Given 教练 C 已登录且 coach.status = 1
And   教练 C 名下有 3 份 active 套餐
When  教练 C 填写离职原因="个人发展"并提交申请
Then  coach.status 更新为 4（申请中）
And   系统生成 1 条离职工单 ticket.status = "processing"
And   工单中学员清单包含 3 份套餐及其剩余课时
And   返回 HTTP 200 与提示"离职申请已提交，请处理学员套餐"
```

### 6.2 场景 2：教练登记学员套餐处理结果

```gherkin
Given 教练 C 的离职工单已生成
And   学员 S 的 package P1（active，剩余 5 课时）在工单中
When  教练 C 选择对 P1 的处理结果="转新教练"
And   填写 target_coach_id=200
And   点击保存
Then  coach_resignation_action 表新增 1 条记录
And   action='transfer'、target_coach_id=200、status='registered'
And   工单进度更新为"1 / 3 已处理"
```

### 6.3 场景 3：非已通过教练无法申请离职

```gherkin
Given 教练 C 的 coach.status = 0（待审核）
When  教练 C 访问「申请离职」入口
Then  入口隐藏或按钮置灰
And   提示"入驻审核通过后可申请离职"
```

### 6.4 场景 4：重复提交离职申请

```gherkin
Given 教练 C 的 coach.status = 4（申请中）
When  教练 C 再次调用提交离职申请接口
Then  返回错误码 RESIGNATION_ALREADY_PENDING
And   HTTP 状态码 409
And   coach.status 保持 4，不生成新工单
```

### 6.5 场景 5：教练登记非自己名下套餐

```gherkin
Given 教练 C 的离职工单已生成
And   package P2 不属于教练 C
When  教练 C 对 P2 提交处理结果="全额退款"
Then  返回错误码 NOT_OWN_PACKAGE
And   HTTP 状态码 403
And   coach_resignation_action 表不写入记录
```

## 8. 边界场景

### 8.1 边界场景 1：教练在管理员审批前撤销离职申请

- **触发条件**：教练提交申请后、管理员审批前，希望继续教学
- **预期行为**：系统允许教练点击「撤销申请」，将 `coach.status` 从 4 恢复为 1，并关闭工单
- **用户可见反馈**：提示「离职申请已撤销，可继续上课」

### 8.2 边界场景 2：教练名下无 active 套餐

- **触发条件**：教练提交离职申请时名下没有 active 套餐
- **预期行为**：系统仍允许提交，工单学员清单为空，可直接提交至管理员审批
- **用户可见反馈**：工单显示「无待处理学员套餐」

### 8.3 边界场景 3：并发提交离职申请

- **触发条件**：教练快速多次点击提交
- **预期行为**：使用幂等键去重，仅生成 1 张工单
- **用户可见反馈**：仅一次成功提示

## 14. 页面级设计决策

### 14.1 离职入口可见性

- **背景**：status=4 期间需要强隐私，不能暴露「申请中」标签
- **选项**：A. 所有状态教练均可见入口；B. 仅 status=1 可见
- **结论**：选择 B，避免待审核/已离职教练误操作
- **影响范围**：教练端「我的」页面

### 14.2 工单中套餐处理选项

- **背景**：需要让教练登记每份 active 套餐的后续安排
- **选项**：A. 仅「退款/继续」；B. 增加「转新教练」
- **结论**：选择 B，与 PRD §5.4.7 的 3 个操作保持一致
- **影响范围**：离职工单处理页、coach_resignation_action 表

### 14.3 页面级交互说明

| 交互 | 触发 | 反馈 | 备注 |
|------|------|------|------|
| 进入申请离职 | 点击菜单 | 弹出确认弹窗 | 提示处理完学员后再提交 |
| 提交申请 | 确认提交 | 跳转工单页 | status 变为 4 |
| 登记处理结果 | 点击套餐行 | 底部弹出 3 个选项 | 转新教练需选择目标教练 |
| 提交至管理员 | 点击按钮 | 提示"已提交审核" | 工单进入 pending_audit |
