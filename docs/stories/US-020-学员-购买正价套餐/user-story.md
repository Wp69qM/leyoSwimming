## 2. 触发条件

- **触发方**：注册用户/学员
- **触发动作**：
  - **入口 A（首页 / 全局套餐列表）**：在首页点击「购买正价套餐」或从全局套餐列表页点击正价套餐卡片 → 进入套餐详情页（未绑定教练）
  - **入口 B（教练详情页 / 教练套餐列表）**：在教练详情页或当前教练的套餐列表页点击正价套餐卡片 → 进入套餐详情页（已携带当前教练信息）
- **触发时机**：用户主动转化时

## 3. 前置条件

- [x] 用户已登录（依赖 US-004 / US-005）
- [x] **入口 A**：系统已配置标准套餐或允许自定义课时（依赖 US-019 / US-045）
- [x] **入口 B**：目标教练已通过入驻审核（依赖 US-011）
- [x] 用户已阅读并同意最新版《用户须知》、健康承诺书、免责协议（§6.9）

- [x] 所选套餐模板 `package_mode='standard'` 且 `status='active'`（已上架）

## 4. 业务流程

### 4.1 主路径

#### 步骤 1：进入套餐详情页

- **入口 A**：用户在首页点击「购买正价套餐」或在全局套餐列表页点击正价套餐卡片，进入套餐详情页（未绑定教练）
- **入口 B**：用户在教练详情页或当前教练的套餐列表页点击正价套餐卡片，进入套餐详情页（已携带当前教练信息）

#### 步骤 2：套餐详情页展示教练选择

1. 套餐详情页根据套餐类型展示不同信息：
   - **标准套餐**：套餐类型、课时数、有效期、价格、套餐包含服务、购买须知
   - **自定义套餐**：套餐类型、参考单价、默认课时选项（4 / 8 / 12 / 20）、有效期选项（30 / 60 / 90 / 180 天）、可学习泳姿、购买须知
2. 页面底部展示教练卡片区：
   - **入口 A**：未绑定教练，展示**横向滚动的适配教练竖向卡片**（头像、姓名、评分、擅长泳姿、教龄、总学员数、**参考单价**），用户必须选择一位教练后才能点击「立即购买」；仅有一位适配教练时默认选中
   - **入口 B**：已携带当前教练信息，展示**当前教练横向自适应卡片**（头像、姓名、评分、擅长泳姿、教龄、总学员数、**参考单价**），无需再次选择
   - 自定义套餐教练卡片需额外展示参考单价，用于后续计算总价

#### 步骤 3：进入确认订单页 / 自定义套餐配置页

3. 用户点击「立即购买」：
   - **标准套餐**：进入确认订单页
   - **自定义套餐**：进入自定义套餐配置页

4. **标准套餐确认订单页**展示：
   - 教练横向自适应卡片信息（头像、姓名、评分、擅长泳姿、教龄、总学员数）
   - 套餐信息
   - 价格信息
   - 《用户须知》、健康承诺书、免责协议勾选区

5. **自定义套餐配置页**展示：
   - 教练横向自适应卡片（头像、姓名、评分、擅长泳姿、教龄、总学员数、**参考单价**）
   - 课时数量：默认选项 4 / 8 / 12 / 20，支持自定义输入其他正整数
   - 有效期：默认选项 30 / 60 / 90 / 180 天
   - 学习泳姿：多选
   - 价格明细：根据所选课时数 × 参考单价实时计算
   - 《用户须知》、健康承诺书、免责协议勾选区

#### 步骤 4：提交订单

6. 用户勾选协议后点击「确认订单」/「提交订单」
7. 系统校验：所选教练 status=1、用户无其他教练的 active 套餐、协议版本正确、未成年人用户信息中已维护监护人手机号、套餐模板 `package_mode='standard'` 且 `status='active'`、自定义课时数/有效期/泳姿在允许范围内
8. 系统将模板关键字段快照写入订单/预生成 package：package_name、package_mode、coach_id、coach_name、teaching_type、stroke_ids、total_hours、duration_minutes、valid_days、original_price、paid_amount、refund_enabled、refund_ratio、refund_valid_days、tags、description、images
9. 系统生成待支付订单（order.status=待支付，course_type=1）
10. 系统记录协议签署（agreement_sign）
11. 系统返回订单信息，前端跳转支付页（US-025）

#### 步骤 5：支付

13. 用户在支付页选择支付方式并点击「确认支付」
14. 支付成功后套餐购买流程结束（支付成功后的状态流转由 US-025 承接）

### 4.2 异常分支

- **分支 1**：用户未同意协议 → 返回错误码 `AGREEMENT_REQUIRED`
- **分支 2**：用户已持有其他教练的 active 套餐 → 返回错误码 `COACH_CONFLICT`，引导先更换教练（US-022）
- **分支 3**：教练 status ≠ 1 → 返回错误码 `COACH_UNAVAILABLE`
- **分支 4**：未成年用户信息中未维护监护人手机号 → 返回错误码 `GUARDIAN_PHONE_REQUIRED`，引导前往 US-005 完善资料
- **分支 5**：所选套餐模板 `package_mode ≠ 'standard'` 或 `status ≠ 'active'` → 返回错误码 `PACKAGE_NOT_AVAILABLE`
- **分支 6**：自定义套餐课时数、有效期或泳姿不在允许范围内 → 返回错误码 `INVALID_CUSTOM_PACKAGE_CONFIG`
- **分支 7**：同一教练存在未支付订单 → 返回现有待支付订单（幂等）

## 8. 边界场景

### 8.1 边界场景 1：重复提交幂等

- **触发条件**：用户 5 秒内连续两次点击提交
- **预期行为**：第二次返回同一待支付订单，不重复创建
- **用户可见反馈**：继续进入支付页

### 8.2 边界场景 2：自定义课时越界

- **触发条件**：用户提交自定义课时数为 0 或超过后台最大限制
- **预期行为**：拒绝提交，提示有效课时范围
- **用户可见反馈**："课时数需在 1-50 之间"

### 8.3 边界场景 3：协议版本过期

- **触发条件**：《用户须知》在订单提交前刚更新，用户未重新同意
- **预期行为**：校验失败，返回 AGREEMENT_REQUIRED 并引导重新阅读
- **用户可见反馈**：弹窗提示"《用户须知》已更新，请阅读后购买"

### 8.4 边界场景 4：入口 A 无适配教练

- **触发条件**：用户从首页/全局套餐列表进入确认订单页，但当前无教练适配所选套餐
- **预期行为**：适配教练列表为空，前端提示"暂无可预约教练"
- **用户可见反馈**：列表空状态，禁用提交按钮

## 14. 页面级设计决策

### 14.1 协议确认交互

- **背景**：正价套餐购买需用户同意《用户须知》、健康承诺书、免责协议三份文件（§6.9），协议文本较长（单份 2000+ 字），若直接平铺会导致购买页过长、转化漏斗在协议阅读环节流失；同时未勾选协议是高频异常分支（场景 §6.3），需要明确的视觉反馈防止用户卡住。
- **选项**：
  - A. 协议全文平铺在购买表单中 —— 优点：用户必读；缺点：页面过长，转化率低，移动端滚动体验差
  - B. 购买页底部固定「我已阅读并同意」勾选区 + 点击展开协议全文弹窗 —— 优点：页面简洁、协议可按需查看、勾选区始终可见；缺点：用户可能不点开直接勾选（通过协议版本号留痕规避法律风险）
  - C. 提交订单时才弹窗强制阅读协议 3 秒后方可勾选 —— 优点：强制阅读；缺点：阻断转化流程，用户反感
- **结论**：选择 B。购买页底部固定勾选区，点击协议名称弹出全文弹窗；若用户未勾选即提交，弹窗提示"请先阅读并同意协议"并滚动定位到勾选区
- **影响范围**：正价套餐购买页（US-020）、协议确认弹窗组件、协议签署状态查询接口（`/api/agreement/status`）

### 14.2 自定义课时输入

- **背景**：US-019 暴露了两种套餐形态——标准套餐（固定课时）和自定义课时（学员自选节数）。自定义课时需在教练参考单价基础上实时计算金额，同时受后台配置的最大课时数约束（§5.3.4）。若输入越界不实时反馈，用户填完提交才报错，体验差且产生无效订单请求。
- **选项**：
  - A. 仅展示输入框 + 提交时校验 —— 优点：实现简单；缺点：错误后置，用户需重新填写，转化漏斗断裂
  - B. 输入框实时计算金额 + 越界时输入框变红并禁用提交按钮 —— 优点：即时反馈、防止无效提交、金额可见增强信任；缺点：需前端实时计算逻辑
  - C. 步进器（- / +）按 1 递增，限制 1-50 —— 优点：杜绝越界输入；缺点：用户填 30 节需点 29 次，效率低
- **结论**：选择 B。默认展示"教练参考单价 × 课时数 = 订单金额"，输入框支持手动输入；超出后台最大课时数（默认 50）时输入框实时变红、下方提示"课时数需在 1-50 之间"，并禁用提交按钮
- **影响范围**：正价套餐购买页（US-020）、自定义课时输入组件、订单金额展示区

### 14.3 套餐价格展示形式

- **背景**：教练入驻时设置了"参考单价"（US-011），同时后台可配置"标准套餐"（如 10 节套餐，US-045）。学员在购买页看到的价格信息来源不统一——自定义课时按"参考单价 × 课时"计算，标准套餐是固定价。若只展示一种，学员无法判断套餐是否划算，可能放弃转化；若信息过载，又干扰决策。需明确价格展示的优先级和形式。
- **选项**：
  - A. 仅展示教练参考单价 × 课时 —— 优点：信息单一清晰；缺点：标准套餐的打包优惠不可见，学员无法感知套餐性价比
  - B. 仅展示固定套餐价 —— 优点：决策简单；缺点：自定义课时场景无价格参考，学员不敢提交
  - C. 双展示：标准套餐展示"套餐价 + 单节均价"，自定义课时展示"参考单价 × 课时 = 总价" —— 优点：两种场景都有清晰价格锚点、学员可对比套餐性价比；缺点：信息密度较高，需设计层级区分
- **结论**：选择 C。标准套餐卡片展示「套餐价 ¥XXX（¥XX/节）」突出性价比；自定义课时区展示「参考单价 ¥XX/节 × N 节 = ¥XXX」突出计算透明度；两者视觉同级，由学员切换 Tab 选择
- **影响范围**：正价套餐购买页（US-020）、套餐选择 Tab 组件、价格展示组件；间接影响 US-019（套餐浏览页价格展示一致性）

### 14.4 未成年人监护人信息收集时机

- **背景**：PRD §6.9 要求未成年人购买正价套餐必须填写监护人手机号并通过短信校验，订单创建后向监护人发送通知。监护信息是强校验项（场景 §6.4 未填返回 `GUARDIAN_PHONE_REQUIRED`）。收集时机影响转化率与数据完整性——过早收集打断浏览，过晚收集导致提交失败需返工。
- **选项**：
  - A. 用户注册时（US-005）强制收集监护人手机号 —— 优点：一次性收集、下单流程顺畅；缺点：注册阶段增加摩擦、成年用户被干扰、未成年人在注册时可能未带监护人手机
  - B. 提交订单时弹窗收集 + 短信校验 —— 优点：仅在需要时触发、不打扰成年用户；缺点：下单流程末端增加步骤、短信校验等待可能流失
  - C. 点击"购买"后进入引导页收集监护人信息，再进入支付确认页 —— 优点：流程分段清晰、收集完整；缺点：多一个页面跳转、转化路径变长
- **结论**：选择 B。仅在系统识别用户年龄 < 18 且用户点击提交订单时弹窗收集监护人手机号；MVP 阶段仅校验手机号已填写，不触发短信验证码校验；校验通过后继续提交订单，校验失败则停留在弹窗；成年用户无感知。监护人手机号写入 `guardian_contact` 表，订单创建后触发监护人短信通知。短信验证码校验为 MVP 后增强项。
- **影响范围**：正价套餐购买页（US-020）、监护人信息收集弹窗组件、短信校验接口（`/api/guardian/verify`）；间接影响 US-021（套餐详情页监护人信息回显）、US-025（支付页不需要重复收集）
