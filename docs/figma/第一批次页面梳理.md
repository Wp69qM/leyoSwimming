## 2. 待办任务清单

### 任务 1：按 api-convention 修正 API 路径与技术设计

**目标**：让所有 US 的 API 命名统一符合 [docs/tech/api-convention.md](../tech/api-convention.md) 的 RPC over HTTP 规范。

**检查与修改范围**：
- 每个 US `user-story.md` §7.2 API 影响表
- 每个 US `tech-design.md` §4 API 设计
- 每个 US `test-plan.md` 中引用的接口路径（如有）

**规范要点**：
- 统一使用 `POST`
- URL 结构：`/api/{模块}/{资源单数}/{动作}`
- 禁止 URL 路径参数：`{id}` 改为 JSON body 中的 `{资源}Id`
- 常用动作：`list`、`detail`、`add`、`update`、`delete`、业务动词（`approve`/`reject`/`login`/`logout` 等）
- ID 字段命名使用 lowerCamelCase，如 `applicationId`、`coachId`、`userId`

**输出**：每个 US 的 API 表与 tech-design 中所有接口路径符合规范，无路径参数残留。

---

### 任务 2：检查 user-story / tech-design / test-plan 三件套一致性

**目标**：确保同一个 US 的三份文档口径一致，没有互相矛盾或遗漏。

**检查项**：
- 业务流程（user-story §4）与技术设计中的接口/数据模型/状态机一一对应
- 验收标准（user-story §6）能被 test-plan 中的测试用例覆盖
- 数据表影响（user-story §7.1）与 tech-design §3 数据模型一致
- 状态机影响（user-story §7.3）与 tech-design §5 一致
- 错误码在 user-story、tech-design、test-plan 中命名与含义一致

**输出**：每个 US 三件套无冲突；如有冲突，记录并修复。

---

### 任务 3：检查 OpenSpec 变更产物

**目标**：每个 US 都有完整的 OpenSpec change，且内容符合 [AGENTS.md](../../.trae/rules/common/agents.md) 与 OpenSpec 规范。

**检查项**：
- `openspec/changes/us-NNN-.../` 目录存在
- 四件套齐全：`proposal.md`、`design.md`、`specs/.../spec.md`、`tasks.md`
- `.openspec.yaml` 存在且 `schema: spec-driven`
- proposal 聚焦 Why / What，capabilities 使用 kebab-case
- spec 使用 `## ADDED Requirements delta` 与 `### Requirement: REQ-XXX` 格式
- design 包含数据模型、API、缓存策略、性能指标
- tasks 每个任务 2-5 分钟可执行，标注 REQ-XXX 与 Scenario，无 placeholder
- 与 `docs/stories/US-NNN-.../` 三件套内容一致

**输出**：缺失或不一致的 OpenSpec change 补齐/修正；运行 `openspec validate --change <name>` 通过。

---

### 任务 4：清理 user-story 中 Figma 链接占位，确保 page-spec 链接完整

**目标**：user-story §13 只保留 page-spec 链接，不再填写 Figma file URL / node-id。

**检查项**：
- 删除或不再保留 "Figma file URL 待设计填写"、"frame node-id 待设计填写" 等占位行
- 表格列头统一为 `内容 | 链接 | 状态`
- 每个 US 涉及的所有页面都有对应的 page-spec 链接
- 链接路径正确：`../../figma/page-spec/<page-spec-name>.md`

**输出**：每个 US 的 §13 Figma 链接区只含 page-spec 引用，整齐一致。

---

### 任务 5：核对并更新 page-spec 与用户故事的相关性

**目标**：确保 page-spec 准确描述当前 US 需要的页面，补齐缺失页面，删除过时内容。

**检查项**：
- page-spec 文件名与 Frame 命名符合 [figma-frame-organization.md](./figma-frame-organization.md)
- page-spec 中的元素清单、显隐规则、跳转矩阵覆盖 US 中描述的所有页面状态
- 新增页面（如任务 4 发现缺失）按 [TEMPLATE.md](./page-spec/TEMPLATE.md) 创建 page-spec
- 多个 US 共享的页面 page-spec 归属明确，交叉引用一致

**输出**：
- 每个 US 涉及的 page-spec 都存在且内容准确、为最新版本
- **将确认无问题的 user-story.md 顶部状态从 `[REVIEW]` 更新为 `[APPROVAL]`**

---

### 任务 6：通过 Calicat MCP 对比设计稿并更新 frame node-id

**目标**：在 Calicat 设计稿中找到对应 Frame，验证元素与 page-spec 一致，并把 node-id 写回 page-spec。

**执行步骤**：
1. 获取 Calicat file_id（项目配置或 Calicat 文件 URL）
2. 对每个 page-spec：
   - 使用 `get_design_page_list` 或 `get_meta_data` 查找对应 Frame
   - 使用 `get_design_data` / `get_interaction_design_data` 读取 Frame 结构与交互
   - 核对 Frame 内元素与 page-spec §3 元素清单是否一致（至少关键元素不缺）
   - 在 page-spec 中补充或更新 Figma/Calicat file URL 与关键 Frame 的 node-id

**输出**：每个 page-spec 包含准确的 Calicat/Figma file URL 与关键 Frame node-id，设计稿与规格一致。

## 3. 建议执行顺序

1. **先统一修正 API 规范（任务 1）**，因为 API 路径会影响 tech-design、test-plan 和 OpenSpec tasks。
2. **再跑三件套一致性（任务 2）**，修复因 API 调整带来的冲突。
3. **同步补齐 OpenSpec 四件套（任务 3）**，必要时用 `openspec update-change` 同步。
4. **清理 Figma 链接（任务 4）** 与 **更新 page-spec（任务 5）** 可并行按端分组执行。
5. **最后做 Calicat 校验（任务 6）**，因为依赖设计稿已存在。
